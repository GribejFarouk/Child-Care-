\chapter{Conception}
\label{chap:conception}

\section*{Introduction}
Ce chapitre décrit la conception technique de ChildCare+. Il présente l'architecture globale, les microservices, la sécurité, le modèle de données et les scénarios de séquence retenus.

% -------------------------------------------------------------------
\section{Le modèle architectural}
\label{sec:architecture}

ChildCare+ adopte une architecture microservices. Le frontend React communique avec une passerelle Nginx qui redirige les requêtes vers les services Django REST Framework. Chaque service dispose de sa propre base PostgreSQL afin de séparer les responsabilités et de réduire le couplage entre domaines. La figure suivante synthétise cette organisation autour de quatre éléments principaux : interface web, passerelle API, services métier et bases de données.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.95\textwidth]{architecture_globale.png}
\caption{Architecture globale de ChildCare+}
\label{fig:architecture-globale}
\end{figure}

\subsection{Architecture logique}

L'architecture logique est organisée en quatre couches :

\begin{enumerate}
    \item \textbf{Couche présentation :} application React contenant l'espace parent, l'espace médecin, l'assistant santé et les pages de consultation.
    \item \textbf{Couche passerelle :} Nginx centralise les routes publiques et bloque les endpoints internes.
    \item \textbf{Couche métier :} microservices Django spécialisés par domaine.
    \item \textbf{Couche données :} bases PostgreSQL isolées par service.
\end{enumerate}

\section{Sécurité et contrôle d'accès}

\subsection{Authentification}
L'authentification repose sur des jetons JWT émis par Auth Service. Les services valident les jetons à l'aide d'une clé de signature partagée. Les routes sont séparées selon le rôle parent ou médecin.

\subsection{Permissions médecin}
Le parent contrôle précisément les sections partagées avec le médecin. Les permissions possibles couvrent notamment : profil, mesures, courbes, alertes, calendrier, OCR, messagerie et consultation. Lorsqu'un médecin demande une ressource, le service concerné vérifie l'existence d'un partage actif auprès du Collaboration Service.

\subsection{Endpoints internes}
Les communications service-à-service utilisent un jeton interne transmis dans l'en-tête \texttt{X-Internal-Service-Token}. Les routes contenant \texttt{/internal/} sont bloquées côté Nginx pour empêcher leur appel direct depuis l'extérieur.

\subsection{Audit et confidentialité}
Les actions sensibles sont envoyées au Audit Service. Les métadonnées sont filtrées afin d'éviter l'enregistrement de mots de passe, jetons, textes OCR bruts ou liens de consultation. L'assistant santé reçoit uniquement un contexte minimal et ne reçoit pas les documents OCR ni les conversations médecin-parent.

\subsection{Principales entités}

\begin{itemize}
    \item \textbf{CustomUser :} compte utilisateur avec rôle parent ou médecin.
    \item \textbf{Child :} profil enfant rattaché à un parent.
    \item \textbf{Measurement :} événement de mesure contenant poids, taille, IMC, périmètre crânien et champs complémentaires.
    \item \textbf{Alert :} événement signalant une valeur ou une évolution à surveiller.
    \item \textbf{ClinicalFinding :} interprétation déterministe structurée d'un constat, par exemple \texttt{bmi\_below\_reference}.
    \item \textbf{Recommendation :} conseil prudent lié à un score de risque et à des facteurs explicables.
    \item \textbf{OCRImport :} trace d'un document importé, candidats extraits, corrections et mesure confirmée.
    \item \textbf{HealthEvent :} rendez-vous, vaccination, contrôle ou événement médical.
    \item \textbf{Notification :} rappel ou information destinée au parent ou au médecin autorisé.
    \item \textbf{ChildShare :} partage entre parent et médecin avec permissions.
    \item \textbf{Message :} message textuel dans le contexte d'un enfant partagé.
    \item \textbf{ConsultationSession :} session audio/vidéo basée sur un lien externe sécurisé.
    \item \textbf{AuditEvent :} trace d'une action sensible.
    \item \textbf{Conversation et AssistantMessage :} historique du dialogue entre parent et assistant santé.
\end{itemize}

\subsection{Architecture de la table Measurement}

Les mesures anthropométriques sont stockées dans \textbf{une seule table} \texttt{measurements}. Chaque ligne représente une mesure effectuée à une date donnée pour un enfant. Les colonnes sont optionnelles pour permettre une saisie partielle.

Les principaux champs sont : \texttt{weight\_kg}, \texttt{height\_cm}, \texttt{bmi}, \texttt{head\_circumference\_cm}, \texttt{age\_at\_recording\_months}, \texttt{date\_recorded} et \texttt{ocr\_import\_id}. Ce choix facilite l'historisation par visite et évite de disperser les mesures dans plusieurs tables.

\subsection{Références OMS et percentiles}

Le service Analytics contient une couche de référence utilisée à la fois par les courbes et les règles d'analyse. Les références affichées sont :

\begin{itemize}
    \item \textbf{P3 :} limite basse indicative ;
    \item \textbf{P50 :} médiane ;
    \item \textbf{P97 :} limite haute indicative.
\end{itemize}

Les références sont disponibles selon l'indicateur et l'âge. Le périmètre crânien est utilisé principalement jusqu'à 60 mois. Pour les enfants plus âgés, le système indique que la référence n'est pas disponible au lieu de produire une alerte non justifiée.

\subsection{Séparation entre analyse déterministe et IA}

Une règle importante de conception est la séparation des responsabilités :

\begin{itemize}
    \item le \textbf{Analytics Service} calcule les alertes, percentiles, constats et recommandations ;
    \item le \textbf{Assistant Service} explique uniquement ces résultats en langage simple ;
    \item le modèle IA ne décide pas si une mesure est normale ou anormale.
\end{itemize}

Cette séparation rend le système plus contrôlable et plus défendable dans un contexte académique et médical.

\section*{Conclusion}
Ce chapitre a présenté la conception de ChildCare+ : une architecture microservices, une séparation stricte des responsabilités, un contrôle d'accès par rôle et permission, ainsi qu'un modèle de données organisé autour du dossier enfant. Le chapitre suivant décrit la réalisation technique et les interfaces développées.
