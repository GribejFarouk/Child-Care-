\section{Services backend réalisés}
\label{sec:backend-realise}

\subsection{Auth Service}
Ce service gère les comptes utilisateurs, les rôles parent et médecin, l'inscription, la connexion, le rafraîchissement des jetons et la déconnexion. Les mots de passe sont hachés et l'e-mail sert d'identifiant principal.

\subsection{Profile Service}
Ce service gère les profils parent, médecin et enfant. Il contient aussi les informations utiles telles que allergies, groupe sanguin et données médicales de base. Il expose des endpoints internes pour vérifier qu'un parent possède bien un enfant.

\subsection{Measurements Service}
Ce service stocke les mesures, calcule l'IMC, valide les valeurs saisies et empêche les doublons issus d'une double confirmation OCR. Les médecins peuvent lire les mesures seulement si la permission correspondante est accordée.

\subsection{Analytics Service}
Ce service centralise les références OMS, produit les alertes, les recommandations et les constats cliniques. Il calcule des indicateurs explicables, comme une valeur sous P3 ou au-dessus de P97, et fournit un contexte minimal à l'assistant santé.

\subsection{OCR Service}
Le service OCR accepte des images ou PDF, vérifie le type réel du fichier, limite les PDF volumineux, applique des prétraitements et extrait plusieurs candidats. La mesure finale n'est créée qu'après validation explicite par le parent.

\subsection{Calendar Service}
Ce service gère les rendez-vous, vaccinations, contrôles et événements médicaux. Les événements dépassés passent en attente de confirmation, puis le parent choisit s'ils ont été effectués ou non.

\subsection{Collaboration Service}
Ce service gère les partages parent-médecin, les codes, les permissions, la révocation, la messagerie et les sessions de consultation audio/vidéo par lien externe.

\subsection{Notification Service}
Ce service stocke les notifications, fournit le compteur non lu, permet le marquage comme lu et reçoit les événements internes créés par le calendrier ou l'analyse.

\subsection{Audit Service}
Ce service journalise les actions sensibles : accès au dossier, partage, modification de permissions, OCR, consultation, assistant et autres événements importants. Le parent peut consulter un journal d'activité filtré.

\subsection{Assistant Service}
Ce service gère les conversations parent-assistant. Il vérifie la propriété de l'enfant, récupère un contexte minimal auprès du service Analytics, applique des garde-fous et appelle Gemini Flash Lite lorsque l'IA est activée. En cas d'indisponibilité, une réponse déterministe de secours est utilisée.

\section{Interfaces de la plateforme}
\label{sec:interfaces}

\subsection{Interface parent}

L'espace parent contient :

\begin{itemize}
    \item un tableau de bord avec enfants, prochain rendez-vous, recommandations et équipe médicale ;
    \item une page enfants pour gérer les profils et consulter les mesures ;
    \item un formulaire d'ajout de mesure ;
    \item des courbes de croissance avec P3, P50, P97 et IMC ;
    \item un centre d'alertes et de constats cliniques ;
    \item un assistant santé avec historique de conversation ;
    \item un calendrier médical avec événements à venir, à confirmer et historique ;
    \item une page médecins pour créer, modifier ou révoquer les partages ;
    \item un import OCR avec revue manuelle ;
    \item un journal d'activité.
\end{itemize}

\subsection{Interface médecin}

L'espace médecin contient :

\begin{itemize}
    \item un tableau de bord avec patients partagés, messages, alertes et prochains rendez-vous ;
    \item une page Mes Patients avec acceptation d'un code de partage ;
    \item un dossier patient composé d'onglets affichés selon les permissions ;
    \item l'accès aux courbes lorsque la permission \textit{courbes} est accordée ;
    \item la messagerie avec le parent ;
    \item les boutons de consultation audio/vidéo lorsque la permission est active ;
    \item l'historique des consultations.
\end{itemize}

\subsection{Suppression des données simulées actives}

Les premières versions utilisaient des données simulées côté frontend. Une phase de stabilisation a retiré les dépendances actives à ces données. Le frontend nécessite maintenant un backend en exécution et affiche des états vides honnêtes lorsque les données n'existent pas.

\section{Exécution locale}
\label{sec:execution}

Le backend se lance avec :

\begin{verbatim}
docker compose up --build -d
\end{verbatim}

Le frontend se lance séparément avec :

\begin{verbatim}
cd frontend
npm run dev
\end{verbatim}

Le frontend est accessible localement via Vite. Les appels API passent par Nginx sur \texttt{http://localhost}, qui redirige ensuite vers les services internes.

\section{Tests et validation}
\label{sec:tests}

La validation a combiné des tests automatisés et des tests manuels. Les tests backend couvrent les services d'authentification, profils, mesures, analyse, calendrier, collaboration, OCR, notifications, audit et assistant. Le build frontend a été vérifié avec \texttt{npm run build}.

Les points vérifiés incluent :

\begin{itemize}
    \item connexion parent et médecin 
    \item isolation des données entre parents 
    \item accès médecin selon permissions 
    \item modification et révocation des partages 
    \item création de mesures, calcul IMC et génération d'alertes 
    \item affichage des courbes OMS 
    \item import OCR, revue, correction et confirmation 
    \item rappels calendrier et événements à confirmer 
    \item notifications et journal d'activité 
    \item messagerie et consultation par lien 
    \item assistant santé avec garde-fous et fallback.
\end{itemize}

\section{Limites actuelles}

Malgré l'avancement du prototype, certaines limites doivent être clairement mentionnées :

\begin{itemize}
    \item les références OMS intégrées restent adaptées au périmètre du projet et ne remplacent pas un outil clinique certifié ;
    \item l'interprétation nutritionnelle des jeunes enfants nécessite prudence, car l'IMC seul ne suffit pas toujours ;
    \item l'OCR dépend fortement de la qualité du document scanné et impose une validation parent ;
    \item l'assistant IA utilise un fournisseur externe et doit être limité aux données fictives ou à une démonstration contrôlée ;
    \item les consultations reposent sur des liens externes, sans infrastructure WebRTC interne ;
    \item le projet n'est pas certifié médicalement et ne revendique pas une conformité réglementaire complète.
\end{itemize}

\section*{Conclusion}
Ce chapitre a présenté la réalisation de ChildCare+. La plateforme dispose désormais d'un ensemble cohérent de fonctionnalités : suivi enfant, mesures, OMS, alertes, assistant, OCR, calendrier, notifications, collaboration, consultations et audit. Ces éléments constituent une base solide pour la démonstration académique et ouvrent la voie à des améliorations futures.
